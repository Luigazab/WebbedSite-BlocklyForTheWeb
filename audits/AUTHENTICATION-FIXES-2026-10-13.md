Authentication remediation for [webbedsite.fun](https://webbedsite.fun), 13 October 2026.

The application and Supabase changes below address findings 1–10. Finding 11 uses the app password-screening alternative explicitly selected by the owner to stay on Supabase Free. Supabase's platform-wide breached-password feature remains disabled because it requires Pro or above. Requests made directly to Supabase Auth can bypass app screening; the platform advisory therefore remains a known limitation of this Free-plan choice.

| Finding | Change and verification |
| --- | --- |
| 1. Anonymous classroom-course access | Applied RLS and revoked anonymous table privileges. Reads require class membership, its owning teacher, or administrator status. Writes require the owner/admin, with checks on both existing and proposed classroom IDs. Live anonymous reads return 401; all anonymous CRUD grants are absent. |
| 2. Public private-profile fields | Revoked anonymous profile access and limited full profiles to owners, admins, and teachers of enrolled students. General name/avatar joins now use a read-only directory containing only id, username, and avatar_url. Live anonymous email queries return 401. Database role simulations verified visibility for every existing account. |
| 3. Missing reset form | Made UpdatePassword a nested child of the Auth layout. Route matching and rendering tests confirm the outlet renders its page. Invalid/missing links display a recovery message instead of a blank screen. |
| 4. Missing session synchronization | Added a managed auth subscription and storage-change listener. Changes are deferred outside Supabase's auth callback; late profile responses cannot restore a signed-out account. Tab-only sessions ignore unrelated BroadcastChannel credentials. |
| 5. Failed login profile loading | Password login is first performed in a non-persisting temporary client. Its profile must load before installing the requested persistent session; failed attempts are revoked. An existing-session profile failure retains authentication and offers retry/sign-out. |
| 6. Remember-me contamination | Persistence is tracked per tab/session. Unchecked login, refresh, and logout preserve another tab's remembered account. Failed login attempts leave the working session and persistence mode intact. |
| 7. Disabled refresh lock | Removed the no-op lock override and restored the SDK's supported coordination. Auth callback work no longer calls the SDK synchronously. |
| 8. Incomplete password recovery | Recovery sessions are tracked separately, cannot enter dashboards, and update completion clears/revokes the session before navigation to login. Failed updates retain recovery so the user can retry. |
| 9. Browser administrator APIs | Deployed admin-auth with verified user JWTs and a fresh server-controlled profile role check. Account creation, reset, status, role, ban/unban, and deletion operations now run there, with returned errors checked. Self-deletion, self-ban, and self-demotion are rejected. No privileged key is included in frontend code. Unauthenticated live requests return 401. |
| 10. Ignored old password | Settings forwards the old password, verifies it in a non-persisting temporary client, and sends current_password with the password update. Incorrect passwords cannot update the account or replace its active session. Verification sessions are revoked afterward. |
| 11. Breached/weak passwords | A deployed read-only password-policy function validates the project API key, enforces 12 characters / 72 UTF-8 bytes, and screens new passwords through Have I Been Pwned's padded hash-range API. Only five SHA-1 hash characters leave Supabase; passwords are never sent to HIBP or logged by this code. Signup, settings, recovery, and administrator password flows use screening; admin screening is enforced in its server endpoint. Provider failures block the operation with a retry message. Live short/known-compromised samples returned 422 and a fresh random sample returned 200. |

The classroom access review also found that existing browser enrollment could bypass join-code validation. Applied a second migration that restricts classroom/member reads, removes direct enrollment privileges, and verifies join codes in a private database function using auth.uid(). Its public wrapper is authenticated-only. A profile-row lock preserves the existing one-classroom rule under concurrent requests. The frontend now calls that RPC; successful teacher/administrator roster access is preserved.

Additional auth hardening includes associated input labels, password-manager autocomplete hints, an account-neutral reset-email acknowledgement, and Netlify response headers for frame restrictions, MIME sniffing protection, and referrer policy.
